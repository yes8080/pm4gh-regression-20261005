## 0. 结论先行

1. **GitHub 原生就能承载完整研发流程**：需求（Issue + 子 Issue + 依赖）、计划（Milestone + Projects）、开发（分支 ↔ Issue 关联）、交付（PR）、评审（Review + Ruleset 必需检查）、验收（Review + 验收记录）、合并（merge + 自动删分支）、发布（Release）。**不需要引入任何外部项目管理工具**。
2. **"一个切片 = 一个 Issue，一个分支 = 一个 Issue"是官方一等公民能力**：`gh issue develop` 建立「Issue ↔ 分支」的绑定，「Development」区块可视化；PR 打开后自动关联；合并到默认分支时按关闭关键字自动关闭 Issue。
3. **有 4 项能力受账号/套餐门控**，必须在动工前决策：**Issue Types、Issue Fields、Merge Queue、多评审人/团队评审**。它们决定了仓库该放在「个人账号」还是「组织」。详见 §1.2 与 §9。
4. **最大现实陷阱是"自己不能批准自己的 PR"**。单人 + 多 AI 工具的场景下，必须用「第二身份（评审/验收机器人账号）+ 必需检查」来构造真实可审计的验收链，否则只能靠 bypass 绕过门禁——那样整套流程就失去意义。详见 §6。
5. **"换开发工具仍能推进"的工程实现只有一条路：所有状态都在 GitHub，本地不留任何私有状态，流程以「配置即代码 + 可执行手册」形式固化在仓库里**。任何新工具（IDE、CLI、AI Agent）只要会 `git` + `gh`，读 `PLAYBOOK.md` 即可接手。详见 §10。

## 1. 事实基线：官方能力与门控

### 1.1 官方确认可直接使用的能力

| 能力 | 官方关键事实 | 用途 |
|---|---|---|
| 子 Issue | 每个父 Issue **最多 100 个子 Issue**，**最多 8 层嵌套**；可在项目视图中按父 Issue 分组/筛选；父 Issue 显示完成进度 | Epic → 切片 → 步骤的层级拆解 |
| 子 Issue CLI | `gh issue create --parent N`；`gh issue edit N --add-sub-issue M` / `--remove-sub-issue` / `--remove-parent` | 全流程脚本化 |
| Issue 依赖 | 「blocked by / blocking」关系；被阻塞的 Issue 在项目看板与 Issue 列表上显示 **Blocked 图标**；`gh issue create --blocked-by/--blocking`、`gh issue edit --add-blocked-by/--add-blocking`、`gh issue view --json blockedBy,blocking` | 表达切片间真实依赖，自动暴露瓶颈 |
| Issue 分支 | 「Create a branch」从 Issue 建分支，显示在 **Development** 区块；**打开 PR 后自动关联到该 Issue**（该分支链接会自动切换为 PR 链接） | 一分支一 Issue 的官方支撑 |
| PR ↔ Issue 关联 | 关闭关键字：`close/closes/closed/fix/fixes/fixed/resolve/resolves/resolved`，写在 **PR 描述**或提交信息中（**PR 标题不解析**）；**仅当 PR 目标是仓库默认分支时**才生效；合并到默认分支即自动关闭被引用 Issue | 交付即闭环 |
| 手动关联 | PR 侧边栏 Development 可手动关联，**每个 PR 最多 10 个 Issue**，且必须同仓库 | 返修/关联场景兜底 |
| Rulesets | 每仓库最多 **75 个 ruleset**，组织级另计 75 个；规则可叠加，**冲突时取最严格**；执行态 `active` / `disabled`（**`evaluate` 评估态仅 Enterprise**）；支持 bypass 名单（`always` / `pull_request` / `exempt` 三种模式） | 用规则而不是靠人自觉 |
| 可用规则 | 要求 PR、要求评审数、**要求 CODEOWNERS 评审**、要求其他审批人、要求解决所有评论、限制合并方式、**要求状态检查通过（strict/loose 两档）**、要求线性历史、阻止 force push、限制创建/更新/删除、要求部署成功、要求签名提交、要求工作流通过、push 规则（路径/扩展名/大小）、`Require merge queue` | 质量门禁的全部原料 |
| 平台级门控（个人 Pro） | **受保护分支**：公开仓库免费；**公开+私有仓库需 Pro**（个人 Pro 私有仓库可用 ✅）；**Rulesets**：公开仓库免费、**公开+私有需 Pro** ✅；**CODEOWNERS**：同上 ✅；**Auto-merge**：同上 ✅；**Environments**：公开仓库全套餐；**私有的环境/部署保护规则需 Pro+** ✅ | 个人 Pro 私有仓库可以拿到完整门禁 |
| 自动删除分支 | 仓库设置 **"Automatically delete head branches"**（`delete_branch_on_merge`）；注意文档明确：分支保护/仓库规则**可能阻止自动删除** | 合并后自动清理远程分支 |
| Projects | 可在**用户级或组织级**创建；每个项目**最多 50,000 条 item、50 个字段**；表格/看板/路线图三种布局；迭代字段（默认自动建 3 个迭代，可插休息期）；内置自动化（默认开启两条：**Issue/PR 关闭 → Status=Done**、**PR 合并 → Status=Done**）；支持按父 Issue 分组/筛选；Insights 图表（图表在 Insights 中，不是一种布局）；状态更新；**项目模板仅组织可用**；视图与字段可用 GraphQL 代码化 | 单一事实源 + 可视化 + 度量 |
| Milestone | 里程碑页显示完成百分比、开关数量、可拖拽排序（超过 500 个未关闭 Issue 时不能手动排序） | 里程碑燃尽与范围管理 |
| Issue Fields（2026-07-02 GA） | **组织级**：Free / Team / Enterprise / GHEC 所有组织的所有仓库共享；每组织**最多 25 个字段**、单选字段最多 100 个选项、每种 Issue Type 最多钉 10 个字段；默认 4 个字段（Priority / Effort / Start date / Target date）；支持 MCP 读取写入 | 用类型化元数据替代"标签凑合" |
| Issue Types | 官方文档为**组织级**能力：由组织所有者创建管理，默认 Task / Bug / Feature，可自定义，**每组织最多 25 个**；可作为 Projects 的筛选/分组维度 | 承载 Feature / Task / Bug / Spike 等语义 |
| 第三方编码 Agent | Claude / OpenAI Codex 等第三方编码 Agent 需**付费 Copilot 套餐**；`gh agent-task create/list/view`（preview）可创建/查看 Agent 任务 | 多工具协作的可选加速器 |

### 1.2 门控矩阵（决定架构的关键）

| 能力 | 个人 Pro + 私有仓库 | 组织 Free + 私有 | 组织 Team + 私有 | 组织 + 公开仓库 |
|---|---|---|---|---|
| Issue / 子 Issue / 依赖 / Milestone / Labels | ✅ | ✅ | ✅ | ✅ |
| Projects v2（含 50k item / 50 字段） | ✅ | ✅ | ✅ | ✅ |
| 受保护分支 / Rulesets / CODEOWNERS / Auto-merge | ✅ | ❌ | ✅ | ✅ |
| Environments + 部署保护（私有仓库） | ✅ | ❌ | ✅ | ✅（公开仓库全套餐） |
| 组织级 Rulesets（一次管多仓库） | —（个人无组织级） | ❌ | ✅ | ✅ |
| **多评审人 / 团队评审** | ❌ | ❌ | ✅ | ✅ |
| 按路径的 **必需评审人（团队）** | ❌（官方明确：**不适用于用户拥有的仓库，因为没有 team**） | ❌ | ✅ | ✅ |
| **Issue Types（含自定义）** | ❌（官方为组织级） | ✅ | ✅ | ✅ |
| **Issue Fields（GA）** | ❌（官方为组织级） | ✅ | ✅ | ✅ |
| **Merge Queue** | ❌ | ❌ | ❌（官方：私有仓库需 **GHEC**） | ✅ |

**结论**：**Merge Queue 在"私有 + 非 GHEC"下无法使用**，因此方案不依赖它，改用官方 Ruleset 的 **"Require branches to be up to date before merging"（strict 必需检查）+ Auto-merge** 达到等价安全性；Issue Types / Issue Fields 属于组织级红利，方案把它们设计成**可选增强层**，缺失时用 **Projects 单选字段 + Labels** 承载同样的语义。

#### 1.2.1 容易被忽略的门控（官方原文，影响实现方式）

| 能力 | 官方限制 | 对本方案的影响 |
|---|---|---|
| Ruleset `evaluate`（评估态） | REST 文档：**仅 GitHub Enterprise 可用** | ❌ 本方案**不能**用"先评估再启用"的灰度手法；改为"先建最小规则集，逐条加严" |
| Rule Insights 面板 | Team + Enterprise Cloud | ❌ Pro 上无规则命中分析，改用 Action 自建审计报告 |
| `workflows` 规则（必需工作流） | 需组织级 ruleset → **Team+**；且该规则只应用于"所有变更都经 PR"的分支 | ❌ Pro 上"用中心化工作流卡 PR"不可用，改为**本仓库必需状态检查** |
| Push rulesets（路径/大小/扩展名限制） | Team+ | ❌ 不作为方案依赖 |
| 组织级 Rulesets | **Team+**（2025-06-16 起 Team 可用） | 影响 §9 选项 2 的价值 |
| 提交元数据限制（强制分支名/提交信息格式） | Enterprise | ❌ Pro 上**分支命名与提交规范必须由 CI 检查**，不能靠规则集 |
| 多评审人 / 团队评审 | Team+ | 影响 §6.2 |
| Merge Queue | 组织公开仓库 或 GHEC 私有仓库 | 见上 |
| `markProjectV2AsTemplate`（项目模板） | 仅组织拥有的项目 | 影响 §9 |
| Auto-add 自动入库工作流数量 | Free 1 / **Pro 5** / Team 5 / EC 20 | Pro 够用（建议只建 1~2 条） |
| 组织级 Ruleset **不能**包含 `merge_queue` 与 `required_deployments` | 官方明确为仓库级专属 | 与 Pro 无关，但迁移到组织后要记住 |

> 实现层面的直接后果：**在个人 Pro 上，"用规则集一次性锁死所有规范"是做不到的**。规范必须分成两层——**能用规则集表达的（PR 必需、审批数、CODEOWNERS、状态检查、线性历史、禁止强推/删除）走规则集；不能表达的（分支命名、提交信息格式、PR 必须关联 Issue、验收记录）走必需状态检查**。这一分工已体现在 §8。

### 1.3 关键的自动化限制（官方原文）

> `GITHUB_TOKEN` 作用域仅在仓库级，**无法访问 Projects v2**；要访问需 GitHub App（组织项目推荐）或 PAT（用户项目推荐）。

→ 影响：所有"改 Projects 字段"的 Action 必须用 **PAT（存为 secret）** 或 **GitHub App**；官方另提供 `actions/add-to-project` 用于自动入库。

### 1.4 需要"待验证"的三件事（可回滚探针，阶段 0 执行）

1. **个人账号能否创建自定义 Issue Type**：官方只描述组织级管理；`createIssueType` 的入参是 `ownerId`。→ 用一次"创建后立即删除"的 mutation 验证（可回滚）。
2. **`gh` 的 `project` scope**：当前本机 token **缺 `project` scope**，Projects 命令不可用。→ `gh auth refresh -s project`（官方要求在 `gh project` 的手册中明确说明）。
3. **Ruleset 在私有个人仓库的实际生效形态**：个人 Pro **没有 `evaluate` 评估态**（官方仅 Enterprise 提供），因此采用**渐进加严**：先只用 `required_status_checks`（strict），确认 CI 稳定后，再逐步加入 `pull_request`（审批数=0→1）、`require_code_owner_review`、`required_review_thread_resolution`、`required_linear_history`、`non_fast_forward`、`deletion`。每次只加一条，避免一次锁死。**另需实测两点**：①规则集的目标分支写成 `~DEFAULT_BRANCH`（而非 `**`）时，切片分支是否仍能被"自动删除头分支"清理；②必需状态检查在个人私有仓库的可见性与选择条件（官方：该检查须在近 7 天内在本仓库成功过才可被选为必需项）。

## 2. 对象模型（单一事实源）

### 2.1 层级（约定 3 层，远低于官方 8 层上限）

```
Milestone（里程碑 M1）
└── Epic Issue（Feature 类型，1 个里程碑 1~3 个 Epic）
    └── Slice Issue（Task 类型；【一个切片 = 一个 Issue = 一个开发分支 = 一个 PR】）
        └── Step Issue（Task 类型，可选；仅当该切片 > 3 天或需并行时拆）
```

- **一个切片对应一个 Issue**：切片是**可独立验收的最小交付单元**，必须满足 DoR（§5.1）与 DoD（§5.2）。
- 切片大小约束：**1~3 个工作日**、**单 PR 可评审（建议 ≤ 400 行有效 diff）**、**可独立回滚**。
- 切片跨层禁止：不得把"研究/设计/编码/测试"拆成 4 个切片 Issue（那是同一分支内的提交阶段）；切片按**可交付价值**切，不按角色切。

### 2.2 命名与编号规范

| 对象 | 规范 | 示例 |
|---|---|---|
| Milestone | `M<n> <名称>` | `M1 协议与启动闸门` |
| Epic Issue 标题 | `[E<n>] <名称>` | `[E2] 原生子 Issue 工作流` |
| Slice Issue 标题 | `[E<n>-S<k>] <名称>` | `[E2-S3] 用 gh 建立分支并绑定 Issue` |
| Step Issue 标题 | `[E<n>-S<k>-T<m>] <名称>` | 可选 |
| 分支 | `<type>/<issue#>-<slug>`，`type ∈ {slice, fix, hotfix, spike, chore}` | `slice/123-gh-issue-develop` |
| PR 标题 | `[E2-S3] 用 gh 建立分支并绑定 Issue (#123)` | 必须含 Issue 号 |
| PR 描述 | 必含 `Closes #123` | 自动关单 |
| Commit | Conventional Commits + Issue 号 | `feat(issue): bind branch via gh (#123)` |
| 发布标签 | `v<semver>`，与 Milestone 对应 | `v0.3.0` |

### 2.3 状态只在一处：Projects `Status` 字段

**原则：Issue 的 `open/closed` 是 GitHub 的事实状态；研发阶段状态由 Projects `Status` 单选项唯一承载。Labels 不得重复表达状态。**

`Status` 取值与门禁：

| Status | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| `Backlog` | 已识别未就绪 | Issue 已创建、归属 Epic/Milestone | 满足 DoR → `Ready` |
| `Ready` | 可被领取 | DoR 全绿、依赖已清、`Size` 已估、已指派 | 建分支并开工 → `In Progress` |
| `In Progress` | 开发中 | 分支存在且已绑定 Issue、assignee = 执行者 | PR 打开且检查通过 → `In Review` |
| `In Review` | 等待独立评审 | PR 已开、必需检查全绿、描述含 `Closes #N` | ≥1 名非作者评审通过 → `Acceptance`；被打回 → `Rework` |
| `Acceptance` | 等待验收 | 评审通过、CI 通过 | 验收人记录 `/accept` → 合并 → `Done`；验收人 `/reject` → `Rework` |
| `Rework` | 返修中 | 评审或验收打回，且**已给出可核对的返修清单** | 修复提交（同一 PR 分支）→ `In Progress` |
| `Done` | 完成 | PR 已合并到 `main`、Issue 自动关闭、远程分支已删除 | — |
| `Canceled` | 取消 | PM 决策并记录原因 | — |

**`Blocked` 不作为状态**：由官方 `blockedBy` 关系原生表达（看板与列表自动显示 Blocked 图标），避免"状态"被依赖关系污染。

### 2.4 正交维度（用 Labels / Projects 字段表达）

| 维度 | 载体 | 取值 |
|---|---|---|
| 类型 | Issue Types（组织）/ Labels 兜底 | `Feature` `Task` `Bug`（+ 自定义 `Spike` `Chore` `Hotfix`） |
| 优先级 | Projects 单选 `Priority`（或 Issue Field） | `P0` 阻塞 / `P1` 高 / `P2` 中 / `P3` 低 |
| 规模 | Projects 数字 `Size`（故事点或人天） | 1 / 2 / 3 / 5 / 8 |
| 迭代 | Projects 迭代字段 `Iteration` | `Iteration 1..n`（含休息期） |
| 领域 | Labels `area/*` | `area/issue` `area/project` `area/ci` … |
| 角色 | Labels `role/*` | `role/dev` `role/review` `role/qa` `role/release` |
| 来源 | Labels `src/*` | `src/rework` `src/bug` `src/tech-debt` |
| 风险 | Labels `risk/*` | `risk/breaking` `risk/security` `risk/data` |

Label 上限：**只用单一含义、可判定、可机器读取的标签**；禁止"过程性标签"（如 `wip`）与状态双写。官方 2026-08-27 已上线 **label archiving（GA）**，废弃标签可归档而非堆积。

**官方硬约束（影响字段设计）**：
- **Labels 不能驱动 Projects 字段，也不能作为看板/视图的分组维度**（官方明确 group-by 不支持 labels；看板列字段只能是 single-select 或 iteration）。→ 因此 §2.3 的"状态只在一个地方"不仅是最佳实践，更是**唯一可行解**：状态必须落在 Projects 的 single-select `Status` 上，标签只能用于过滤/切片。
- **Issue Types 与 Issue Fields 是组织级能力**，个人账号的 Projects 无法使用这两类字段（Projects 里对应的是"隐藏的 Type 字段"，官方亦说明为组织级）。

## 3. 分支模型

```
main ──●────●────────●──────────●──────► 唯一长期分支，受 Ruleset 保护
        \    \        \        /
         \    \        \      hotfix/321-...   （线上故障，从 main 拉，PR 回 main）
          \    \        slice/123-...          （切片，从 main 拉，PR 回 main）
           \    fix/205-...                    （开发期 bug）
            spike/140-...                      （技术验证，可只产出文档）
```

规则：

1. **`main` 是唯一长期分支**，任何改动必须经 PR；**禁止直接 push**。
2. **每个 Issue 一个分支**，用 `gh issue develop <issue#> --base main --name <type>/<issue#>-<slug> --checkout` 创建，从而获得官方的 Issue ↔ 分支绑定与 Development 区块可见性。
3. **合并方式只允许 Squash**（配合"要求线性历史"规则），保证 `main` 历史一条直线、每次合并对应一个 Issue、可单独 revert。
4. **合并后立即删除头分支**：仓库设置 `delete_branch_on_merge = true`（官方自动删分支）+ 本地 `git branch -d` + `git fetch --prune`。
   - 注意官方警告：**分支保护/仓库规则可能阻止自动删除** → 因此 Ruleset **只针对 `main`（与 `release/*`）**，绝不写成 `**`，否则切片分支删不掉。
5. **发布分支**：仅在需要维护多个线上版本时创建 `release/<major>.<minor>`；PR 到非默认分支时**关闭关键字不生效**（官方限制），所以发布分支上的修复必须额外手动关联 Issue 并在合并后人工关单——这一点写进 PLAYBOOK 作为检查项。
6. **Hotfix**：从 `main`（或线上 tag）拉 `hotfix/<issue#>-<slug>`，走**同一套** PR 流程（评审 → 验收 → 合并），PR 目标为 `main`，因此 `Closes #N` 正常生效。
7. **分支寿命**：合并即删；未合并且 7 天无提交的分支由每周审计 Action 在 Issue 上提醒，14 天无响应则关闭 Issue 并删除分支（保留记录）。官方另有原生的 **Branches → Stale 视图**（3 个月无提交），可作为兜底人工巡检入口。
8. **分支命名的强制手段**：官方"提交元数据限制"（用正则约束分支名/提交信息）属 **Enterprise**，Pro 不可用 → **分支命名规范由 `policy/branch-name` 必需检查强制**（校验 `^(slice|fix|hotfix|spike|chore)/\d+-[a-z0-9-]+$` 且 Issue 号真实存在且处于 `Ready/In Progress/Rework`）。
9. **标签与发布保护**：为 `v*` 建**标签规则集**（限制创建/更新/删除），保证发布记录不被改写；发布分支 `release/*` 单独建规则集（更严的审批与检查），但仍需注意"非默认分支关闭关键字不生效"的限制。
10. **删除分支的安全姿势**：合并用 `gh pr merge --squash --delete-branch`（官方：同时删本地与远程）；残留清理远程用 `git push origin --delete <b>` 或 `gh api -X DELETE repos/{o}/{r}/git/refs/heads/<b>`；本地 `git branch -d`（仅已合并）而非 `-D`；误删可在 PR 页 **Restore branch** 恢复；**永不删除默认分支、不删除仍有开启 PR 的分支**。

## 4. 端到端工作流（全部走 GitHub）

### W0 仓库基线（一次性）

1. 新建仓库（归属见 §9 决策），开启 Issues、Projects、Discussions。
2. `gh auth refresh -s project`（Projects 命令所需 scope）。
3. 配置仓库：
   - `delete_branch_on_merge = true`
   - 只允许 Squash（禁用 merge commit / rebase merge）
   - `allow_auto_merge = true`
4. 落地 `.github/` 骨架与 `docs/PLAYBOOK.md`（§11）。
5. 建 Ruleset：`main-protection`——**渐进加严**：先只含 `required_status_checks`（strict），CI 稳定后再逐条加入 `pull_request`（审批数 0→1）、`require_code_owner_review`、`required_review_thread_resolution`、`required_linear_history`、`non_fast_forward`、`deletion`（个人 Pro 无 `evaluate` 评估态可灰度）。
6. 建 Projects，定义字段与视图（§7），开启内置自动化。
7. 建 Milestone `M1`。

### W1 里程碑立项

1. 用 `milestone.yml` 模板建 Issue，标题 `[M1 Plan] ...`，描述含：目标、验收口径、范围外事项、目标日期。
2. 创建 GitHub Milestone `M1 — <名称>`（`gh` 无 `milestone` 子命令 → 走 REST API `POST /repos/{owner}/{repo}/milestones`，或 `gh issue create --milestone` 时自动创建）。
3. 把该里程碑范围内的 Epic 全部挂到 Milestone 上。

### W2 Epic 与切片立项

1. 建 Epic Issue（类型 `Feature`），模板含：业务目标、验收场景、切片清单、依赖、影响面、风险、回滚方案。
2. 逐条建切片 Issue：`gh issue create --parent <epic#> --type Task --milestone <M1> --label area/...,role/dev --title "[E2-S3] ..."`。
3. 用 `gh issue edit <slice#> --add-blocked-by <other#>` 建立切片间依赖。
4. 切片必须写清 **DoR 五项**（§5.1），否则停在 `Backlog`。

### W3 领取与开工

1. 执行者从 `Ready` 队列自领：`gh issue edit <n> --add-assignee @me`。
2. **`gh issue develop <n> --base main --name <type>/<n>-<slug> --checkout`** —— 一次性完成"建分支 + 绑定 Issue + 切到本地"。
3. Projects `Status` 置 `In Progress`（内置自动化或脚本）。
4. 在 Issue 下留一条"开工声明"评论（分支名、预计交付、依赖状态），形成可审计时间线。

### W4 开发与提交

1. 小步提交，Commit 信息遵循 Conventional Commits 并带 Issue 号。
2. 本地/CI 自检：`scripts/selfcheck.sh`（format / lint / test / docs）。
3. **禁止**在切片分支上改与切片无关的文件（评审时按 CODEOWNERS 自动找对应负责人）。

### W5 交付 PR

1. `gh pr create --base main --title "[E<n>-S<k>] ..." --body-file pr-body.md`。
   - 分支由 `gh issue develop` 创建时，PR 会自动关联到该 Issue；**但 `Closes #N` 仍必须显式写进 PR 正文**。
   - **不要用 `--fill` 代替正文**：官方 CLI 行为是"单提交时把提交信息（含正文）带入 PR 正文；**多提交时只带提交标题、丢弃正文**"，因此多提交时 `--fill` 会把 `Closes #N` 丢掉，导致不建立链接、不自动关单。
2. PR 描述用 `.github/PULL_REQUEST_TEMPLATE.md`，必填：
   - `Closes #<slice#>`（**必须**，机器校验）
   - 变更摘要 / 影响面 / 回滚方式
   - **验收证据**：如何复现与验证（命令、截图、日志、测试名）
   - 自查清单（DoD）
   - 风险与破坏性变更
3. 挂标签 `role/review`，指定评审人（≥1）。
4. Projects `Status` → `In Review`。

### W6 独立评审

1. 必需检查（§8）全绿 + `main` 已同步（strict）。
2. 评审人（**非作者**）按检查清单审：正确性、边界、可维护性、测试充分性、文档、安全、性能。
3. 结论只有三种：
   - `Approve` → `Status: Acceptance`
   - `Request changes` → `Status: Rework` + **必须写可核对的返修清单**（条目化、可逐条勾选）
   - `Comment` → 不改变门禁状态
4. **评审人不得是作者**；若确实只有一个人，走 §6.2 的第二身份方案。

### W7 验收

1. 验收人（通常 ≠ 评审人）按 **验收标准（DoD）逐条核对**，不看代码也应按 PR 描述中的"验收证据"复现一次。
2. 通过：在 PR 上评论 `/accept` 并附核对结果 → 触发 `qa/acceptance` 必需检查通过。
3. 不通过：评论 `/reject` + 逐条差距 → `Status: Rework`。

### W8 合并与收尾（闭环必须原子化）

1. `gh pr merge --squash --delete-branch`（合并 + 删远程分支）。
2. `main` 上的必需检查在合并后必须为绿（strict 模式下已保证）。
3. Issue 因 `Closes #N` **自动关闭**（官方行为）。
4. 本地清理：`git checkout main && git pull --ff-only && git fetch --prune && git branch -d <branch>`。
5. Projects `Status` → `Done`（内置自动化：PR 合并 → Done；Issue 关闭 → Done，双保险）。
6. 父 Epic 进度自动更新（官方子 Issue 进度汇总）；Epic 全部切片完成时人工验收 Epic 并关闭。
7. **收尾检查脚本** `scripts/closeout.sh <pr#>`：校验"PR 已合并 / Issue 已关 / 远程分支已删 / 本地分支已删 / Status=Done"，任何一项不满足即报错——**这是防止流程撕裂的关键**。

### W9 返修（验收/评审未通过）

1. 判定：`Request changes` 或 `/reject`。
2. 动作：**不新建分支、不新建 PR**；在同一切片分支继续提交（保证一个 Issue 对应一个 PR 的历史）。
3. 门禁：新提交会**使已有 Approve 失效**（官方规则"推送新提交时驳回过期批准"）→ 必须重新评审。
4. 状态机：`Rework → In Progress → In Review → Acceptance`。
5. 返修必须挂 `src/rework` 标签，用于统计**返修率**（关键质量指标）。
6. **返修轮次上限 2 次**：第 3 次打回必须升级为"切片重切"或"需求澄清"（由 PM 决策并记录），避免无限拉锯。

### W10 Bug 修复（全部走 GitHub）

分两条轨道，判定标准是"是否已合并到 main"：

| 场景 | 处理 |
|---|---|
| 切片未合并时发现缺陷 | 在**同一分支**修复，按 W9 返修流程走（不新建 Issue） |
| 切片已合并后发现缺陷（开发期） | 新建 `Bug` Issue，模板含复现步骤/期望/实际/影响版本；挂到当前 Milestone；用 `fix/<issue#>` 分支 + `Fixes #N` 的 PR 走完整流程 |
| 线上故障 | 新建 `Bug` Issue 并标 `P0`；从 `main` 拉 `hotfix/<issue#>`；可先合并**最小修复**再补测试（必须在同一 PR 中留下 `TODO` 关联的跟进 Issue）；合并后如维护发布分支则 back-merge，并**手动关单**（非默认分支关键字不生效） |
| 依赖/安全问题 | 由 Dependabot/Code scanning 自动开 Issue，纳入同一套流程（不另开旁路） |

**Bug 也是 Issue**：同样要有 Epic/Milestone 归属、DoR、评审、验收。禁止"口头修一下直接提交"。

### W11 换工具/换人交接

见 §10。核心动作：①在 Issue 上写结构化交接块；②状态回落 `Ready` 或停留 `In Progress` 并转派；③确保分支已推送远程、`main` 无未推送本地提交。

### W12 发布

1. Milestone 内 Slice 全 `Done` → PM 触发发布。
2. `gh release create v<x.y.z> --generate-notes`，notes 中列出该里程碑关闭的 Issue。
3. 发布后：Milestone 关闭；未完成切片**显式迁移**到下一 Milestone（不允许静默留在旧里程碑）。

## 5. 门禁定义（DoR / DoD）

### 5.1 DoR（切片可开工，`Backlog → Ready` 的 5 项）

1. **价值**：一句话说明这个切片交付什么用户/系统价值。
2. **验收标准**：可判定的 Given/When/Then 或等价条目，**禁止"优化一下""完善体验"这类不可判定描述**。
3. **边界**：明确不改什么（防范围蔓延）。
4. **依赖**：`blockedBy` 已建立且无未完成阻塞；接口/契约已冻结。
5. **估算与归属**：`Size` 已填、执行者已指派、Milestone 已挂。

### 5.2 DoD（切片可关闭，`Acceptance → Done` 的 8 项）

1. 验收标准逐条有证据（测试名/命令/输出/截图）。
2. 必需 CI 检查全绿（§8）。
3. 独立评审通过（非作者）。
4. 验收人 `/accept` 记录。
5. 无未解决的评审评论（官方规则"要求解决所有评论"）。
6. 文档/ADR 已更新（涉及接口、数据、运维变更时）。
7. 回滚路径明确可执行。
8. PR 已合并、Issue 已自动关闭、远程与本地分支已删、`Status = Done`。

## 6. 角色、权限与现实约束（"模拟真实团队"的核心）

### 6.1 角色定义

| 角色 | 职责 | GitHub 载体 |
|---|---|---|
| PM / Lead | 里程碑立项、切片排序、DoR/DoD 把关、变更控制、返修升级决策 | Issue 模板、Projects 视图、Milestone |
| Maintainer | 仓库设置、Ruleset、CODEOWNERS、Projects 字段、密钥与自动化 | 仓库 admin |
| Author / Dev | 实现、自测、交付 PR、响应评审 | Assignee + 分支 + PR |
| Reviewer | 独立评审（非作者），给 Approve / Request changes | PR Review |
| Acceptor / QA | 按验收标准复现并验收 | PR 评论 `/accept` `/reject` |
| Release | 打 tag、生成 release notes、里程碑治理 | `gh release` |

单人（你）承担 PM + Maintainer + Author；**Reviewer / Acceptor 由第二身份承担**。

### 6.2 现实约束与解法（重要）

> **官方约束 1**：分支保护/规则集要求的批准必须来自**有写权限且非作者**的人——自己不能批自己。
> **官方约束 2**：个人 Pro 的私有仓库**不支持多评审人**，也不支持"按路径的必需评审人（团队）"（该规则**不适用于用户拥有的仓库**，因为没有 team）。

因此给出三档可选（推荐第 1 档）：

| 档 | 做法 | 代价 | 审计强度 |
|---|---|---|---|
| **A（推荐）双身份** | 建第二个 GitHub 账号作为"评审/验收机器人"，加入仓库为 collaborator（写权限）。作者账号提 PR，评审账号做 Review、`/accept`。可再用一个 AI Agent 以该身份执行 | 多一个账号的凭据管理 | **高**：评审与验收记录是真实独立身份，可审计 |
| B 单身份 + bypass | Ruleset 里把 `Repository admin` 放进 bypass 名单，自己 Approve 自己。官方 bypass 支持三种模式：`always`（始终可绕）/ `pull_request`（仅 PR 可绕）/ `exempt`（规则不执行且**不留审计记录**） | 门禁形同虚设，但保留其余检查 | 低：`exempt` 连审计痕迹都没有，**不建议** |
| C 单身份 + 检查替代 | 不要求 approve，把"验收证据"变成**必需状态检查**（Action 校验 PR 描述中的验收块与 `/accept` 评论） | 无独立人 | 中：机器可审计，但无独立判断 |

**本方案按 A 档设计**，同时保留 C 档作为降级路径（若不想多账号）：即 `qa/acceptance` 必需检查在任何档位都启用——它保证"有验收记录"这一事实**不可能被跳过**。

### 6.3 CODEOWNERS 与角色映射

```
# 默认：任何改动都需要项目负责人评审
*                       @yes8080

/docs/                  @yes8080
/.github/               @yes8080
/scripts/               @yes8080
```
- 个人账号没有 team，因此 CODEOWNERS 只能写个人（这也是选择 A 档的另一个理由）。
- 迁移到组织后改为 `@org/maintainers`、`@org/qa`，规则不变——**这正是"配置即代码"的价值**。

## 7. Projects 设计与度量

### 7.1 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `Status` | 单选 | 8 态状态机（§2.3）**唯一状态源** |
| `Priority` | 单选 | P0~P3（若组织已开 Issue Fields，则改用 Issue Field，保持单一来源） |
| `Size` | 数字 | 1/2/3/5/8 |
| `Iteration` | 迭代 | 默认 2 周；含休息期 |
| `Area` | 单选 | issue / project / ci / docs / release |
| `Target date` | 日期 | 承诺日期 |
| `Rework count` | 数字 | 返修轮次（脚本写入，用于度量） |
| 系统字段 | — | Assignees / Labels / Milestone / Parent issue / Sub-issue progress / Linked PRs |

### 7.2 视图

1. **Roadmap**：按 `Iteration` + Milestone，展示 Epic↔Slice 层级与时间线。
2. **Sprint Board**：按 `Status` 分列（含 WIP 上限提示）。
3. **My Queue**：`assignee:@me Status:Ready,In Progress,Rework`。
4. **Review Desk**：`Status:In Review`（含 PR 链接与检查状态）。
5. **Acceptance Desk**：`Status:Acceptance`。
6. **Blocked Wall**：`blockedBy` 非空的全部条目（原生 Blocked 图标）。
7. **Epic Progress**：按 `Parent issue` 分组，看子 Issue 完成度。
8. **Delivery Audit**：`Status:Done` 且按 Iteration 分组，配合 `Rework count`。

### 7.3 度量（每迭代自动生成）

| 指标 | 定义 | 用途 |
|---|---|---|
| 吞吐 | 每迭代 Done 切片数 | 交付速率 |
| 周期时间 | `Ready → Done` 的中位时长 | 流程效率 |
| 评审等待 | `In Review` 停留时长 | 瓶颈定位 |
| **一次通过率** | 未经历 Rework 的切片占比 | 质量核心指标 |
| **返修率** | `src/rework` 切片 / 总切片 | 需求与实现质量 |
| 逃逸缺陷 | 已合并后发现并开 Bug 的比例 | 验收有效性 |
| 阻塞时长 | `blockedBy` 存在期间的总时长 | 依赖治理 |

### 7.4 内置自动化的边界（官方事实）

官方内置工作流只做**状态回写 / 关单**类动作，其余需自己配：
- **默认开启**：①Issue/PR 关闭 → `Status: Done`；②PR 合并 → `Status: Done`。（新项目默认即生效）
- **可开启（官方列出）**：条目加入项目 → `Status: Todo`；**项目状态改变 → 自动关闭 Issue**（反向联动）；按 filter **自动入库**；按 filter **自动归档**（归档保留字段值，可恢复）。
- **子 Issue 进度是"计算字段"而非工作流**：官方提供隐藏字段 **Parent issue**（可分组、可用 `parent-issue:"owner/repo#N"` 过滤）与 **Sub-issue progress**（total/completed/percent）。**官方没有任何"子 Issue 全部完成 → 自动更新/自动关闭父 Issue"的工作流**，父 Issue 的关闭必须由人（或 Action）显式执行。
- **子 Issue 默认继承父 Issue 的 Project 与 Milestone**（2025-09-11 起官方行为）→ 建切片时无需手动入库/挂里程碑，这是"一个切片一个 Issue"能自动进看板的关键。
- **自动入库工作流数量受套餐门控**：Free 1 条 / **Pro 5 条** / Team 5 条 / Enterprise Cloud 20 条。
- **Auto-archive 的 filter 仅支持** `is` / `reason` / `updated`（如 `updated:<@today-14d`）。

因此：
- **不需要写代码**就能得到：合并即 `Done`、关闭即 `Done`、`Status: Done` 反关 Issue、自动入库、自动归档、子 Issue 进度可视。
- **必须 Actions + PAT/GitHub App** 才能做到：`Ready→In Progress` 自动置位、返修自动回退状态、子 Issue 汇总评论到父 Issue、Burn-down 快照、过期分支审计、里程碑报告。
- **视图现在也能代码化**：官方 GraphQL 提供 `createProjectV2View` / `updateProjectV2View` / `deleteProjectV2View`（名称、布局、filter、可见字段）→ §7.2 的 8 个视图可随 `bootstrap` 一键重建，这是"换环境/换组织也能立刻推进"的重要一环。

## 8. 必需状态检查（质量门）

| 检查名 | 内容 | 触发 |
|---|---|---|
| `ci/lint` | 格式与静态检查 | pull_request |
| `ci/build` | 构建 | pull_request |
| `ci/test` | 单元 + 集成测试 | pull_request |
| `ci/contract` | 接口/契约（涉及 API 时） | pull_request |
| `docs/required` | 变更涉及接口/数据时必须有文档或 ADR | pull_request |
| `policy/linked-issue` | PR 描述必须含有效 `Closes #N` 且指向同仓库 Issue | pull_request |
| `policy/template` | PR 模板必填区块非空（摘要/影响/回滚/验收证据/自查） | pull_request |
| `qa/acceptance` | PR 上必须存在授权身份的 `/accept` 记录 | pull_request + issue_comment |

要点：
- **strict 必需检查**（"Require branches to be up to date before merging"）替代 Merge Queue：保证合并前含最新 `main`。多人并发合并时需要手动 `Update branch`，这是无法使用 Merge Queue 的唯一真实代价。
- **规则集与检查的分工**（因 Pro 无 Enterprise 专属规则）：能用规则集表达的走规则集（`pull_request` + 审批数 + `require_code_owner_review` + `required_review_thread_resolution` + `required_status_checks` + `required_linear_history` + `non_fast_forward` + `deletion`）；**不能表达的（PR 必须关联 Issue、分支命名规范、提交信息规范、验收记录）必须走必需状态检查**。
- **官方无"要求 PR 必须关联 Issue"的原生能力**（既无该规则集规则，也无分支保护选项）→ `policy/linked-issue` 是必做项，用 `gh pr view --json closingIssuesReferences` / `gh issue view --json closedByPullRequestsReferences` 判定。
- **官方无"要求分支命名规范"的 Pro 能力**（元数据限制属 Enterprise）→ 分支名规范由 `policy/branch-name` 检查强制。
- **必需检查的 6 个坑（官方 troubleshooting 原文）**：
  1. 检查名格式：普通工作流为 **`<job name>`**；可复用工作流为 **`<job name> / <reusable job name>`**；工作流名/矩阵/触发类型都不参与匹配。
  2. **永不上报 = 永久 pending**。最大原因是工作流被 `paths`/`branches`/commit-message 过滤跳过 → 官方明确建议"**不要要求那些可能被跳过的工作流**"。因此所有必需检查的工作流**不得配置 paths 过滤**。
  3. **只有由 `push` / `pull_request` / `pull_request_review` / `pull_request_target` / `deployment` / `deployment_status`（合并队列再加 `merge_group`）触发的检查才算数**；`workflow_dispatch` 触发的不满足必需检查（外部 App 的检查不受此限）。
  4. 一个检查**必须在本仓库近 7 天内成功过**，才能在规则集里被选为必需项（首次启用时容易踩）。
  5. 可接受的通过态是 `success` / `skipped` / `neutral`；**跳过的 job 上报为 Success，不会阻塞** →
  6. 反过来也意味着：**用"跳过"冒充通过是可能的**，所以策略类检查（`policy/*`、`qa/*`）禁止使用条件跳过，必须真实判定。
- 检查名一旦被引用为必需项，就**不允许随意改名**（改名会导致 PR 永久 pending）；改名流程写入 PLAYBOOK。
- 只用 `gh pr checks --required` 做本地/脚本判定（**退出码 8 = 仍有 pending**），不要用 `--watch` 之外的自造轮询。

## 10. 工具可切换性（最终目标）

### 10.1 三条铁律

1. **状态只在 GitHub**：本地不得存在"只有某个工具知道"的状态（进度表、TODO 文件、IDE 项目配置里的任务列表）。
2. **流程只在仓库里**：`docs/PLAYBOOK.md` + `.github/*` + `scripts/*` 是唯一权威流程描述；任何工具的行为都必须能由它们推导出来。
3. **一切操作可脚本化、可幂等**：每个流程步骤都有 `gh`/REST 命令对应；禁止"只能在某个 GUI 里点"的动作（若某能力只能 GUI 操作，必须记录在 PLAYBOOK 的"人工步骤"清单中并说明原因）。

### 10.2 新工具接入清单（任何 IDE / CLI / AI Agent 都适用）

```bash
# 1) 环境自检（工具接入第一步，必须全绿）
scripts/toolcheck.sh    # 检查 git/gh 版本、gh auth 状态、token scope(含 project)、仓库权限、必需检查名与近 7 天上报情况
# 2) 读三份文档
docs/PLAYBOOK.md  docs/GOVERNANCE.md  AGENTS.md
# 3) 拉取我的队列并开工
gh issue list --label role/dev --search "assignee:@me" --json number,title
scripts/start.sh <issue#>       # gh issue develop + Status=In Progress + 开工评论
# 4) 交付
scripts/deliver.sh <issue#>     # 自检 + gh pr create（自动填模板与 Closes）
```

### 10.3 交接协议（换工具/换人/换 Agent）

在 Issue 上追加固定结构的交接评论：

```markdown
<!-- HANDOFF:v1 -->
- 当前状态：In Progress（Projects Status）
- 分支：slice/123-gh-issue-develop（已推送：是/否）
- 已完成：<可核对条目>
- 未完成 / 下一步：<可核对条目>
- 阻塞：无 / blockedBy #NNN
- 本地未推送提交：无
- 需要接手者先跑：scripts/toolcheck.sh && scripts/resume.sh 123
```

### 10.4 验收方式：**工具切换演练**（本方案的最终验收测试）

**演练定义**：使用一个**此前未参与该项目**的工具 B（另一个 CLI/IDE/AI Agent，甚至换一台机器），**只允许阅读仓库文档 + 使用 `git`/`gh`**，完成一条完整链路：

> 从 `Ready` 队列领一个切片 → 建分支 → 提交 → 提 PR → 全绿检查 → 被独立评审 → 被验收 → 合并 → 分支自动删除 → 本地清理 → `Status=Done`

**通过标准（缺一不可）**：
1. 全程不需要任何口头/聊天补充说明；
2. 不需要手工修补 Projects 状态（自动流转生效）；
3. 无孤儿分支（本地与远程均干净）；
4. Issue ↔ 分支 ↔ PR ↔ 合并记录四者链接完整可追溯；
5. 换工具前后，Projects 视图与度量口径不变。

**骨架的四条实现约束（均由官方文档推出，避免返工）**：

1. **Ruleset 只能"写 JSON + `gh api`"导入**：`gh ruleset` 在本机 CLI 版本中**只有 `check` / `list` / `view` 三个只读子命令**，没有 create/edit/delete。落地方式三选一：`gh api -X POST repos/{owner}/{repo}/rulesets --input rulesets/main-protection.json`（读需 `Metadata:read`，写需 `Administration:write`）／UI 的 **JSON 导入**／官方模板库 [`github/ruleset-recipes`](https://github.com/github/ruleset-recipes)。可选：Terraform 的 `github_repository_ruleset` 资源（可 `terraform import`）。
2. **里程碑的 CRUD 只能走 REST**：本机 `gh` **没有 `milestone` 子命令**；分配里程碑是原生的（`gh issue create/edit --milestone "M1 ..."`），但创建/改名/关闭/删除要 `gh api /repos/{owner}/{repo}/milestones`。
3. **Projects 字段的创建有限制**：`gh project field-create` **不支持创建 iteration 字段**（要 GraphQL `createProjectV2Field` 或 UI）；`gh project item-edit` 对**非草稿条目每次只能改一个字段**；**不能**通过 Projects 字段 mutation 修改 Assignees/Labels/Milestone/Repository（要用对应的 Issue mutation）；不能在同一个调用里"加条目 + 设字段"。视图则可以完全代码化。
4. **项目模板（`markProjectV2AsTemplate`）仅组织可用** → 个人 Pro 下用 `bootstrap.sh` 重建来代替模板。

**`rulesets/main-protection.json` 的关键字段形状（官方 REST 定义，直接照抄不改名）**：

```json
{
  "name": "main-protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "bypass_actors": [],
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 1,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": true,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true,
        "allowed_merge_methods": ["squash"] } },
    { "type": "required_status_checks", "parameters": {
        "do_not_enforce_on_create": false,
        "strict_required_status_checks_policy": true,
        "required_status_checks": [
          { "context": "ci/lint" }, { "context": "ci/test" },
          { "context": "policy/linked-issue" }, { "context": "policy/branch-name" },
          { "context": "qa/acceptance" } ] } }
  ]
}
```

> 注意：`conditions.ref_name.include` 用 **`~DEFAULT_BRANCH`**（等价于 main），**不要用 `**`**；官方明确"分支保护/仓库规则可能阻止自动删除头分支"，把规则集限定在默认分支上，切片分支才能在合并后被自动清理。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 单人无法自我批准 PR | 门禁死锁或形同虚设 | §6.2 A 档第二身份；C 档降级但保留 `qa/acceptance` 必需检查 |
| 无 Merge Queue（私有 + 非 GHEC） | 并发 PR 合并需手动更新分支 | strict 必需检查 + 小切片 + 短生命周期分支；必要时降低并发 |
| 无 Issue Types / Issue Fields（个人套餐） | 分类语义弱 | Projects 单选字段 + Labels 承载；组织迁移后切换，字段映射表预先定义 |
| `GITHUB_TOKEN` 无法访问 Projects v2 | 自动化静默失效 | 用 PAT/GitHub App 存 secret，并在 `toolcheck.sh` 中校验 PAT 有效期与权限 |
| Actions 分钟数消耗 | 私有仓库计费 | 合并 lint+test 到同一个 workflow、缓存依赖、`concurrency` 取消同分支旧运行；**只有非必需检查的辅助工作流才允许用 `paths` 过滤**（必需检查一旦被 paths 跳过就会永久 pending） |
| 状态双写（Label 与 Projects 不一致） | 事实源混乱 | 铁律：状态只在 Projects `Status`；标签只表达正交维度 |
| 返修无限循环 | 进度停滞 | 返修上限 2 次，第 3 次强制重切/澄清并由 PM 记录 |
| 分支残留 | 仓库腐化 | 三保险：自动删头分支 + `closeout.sh` 校验 + 每周审计 Action |
| 检查改名导致 PR 永久 pending | PR 卡死 | 检查名冻结，改名走变更流程（PLAYBOOK 记录） |
| 关闭关键字在非默认分支失效 | Issue 漏关 | 发布分支/hotfix 场景加"手动关单"检查项；`audit.sh` 定期扫描"已合并 PR 但 Issue 仍 open" |
| 里程碑范围蔓延 | 交付延期 | 变更控制：新增切片必须挂 Milestone 并显式迁移未完成项；Milestone 目标日期变更需记录理由 |
| **必需检查被跳过/永不上报** | PR 永久 pending，流程卡死 | 必需检查的工作流禁止 paths/branches 过滤；不要求可能被跳过的工作流；策略与验收类检查禁止条件跳过；`toolcheck.sh` 定期校验必需检查近 7 天内是否上报过 |
| **规则集用 `**` 通配目标** | 头分支无法自动删除 | 规则集目标限定 `~DEFAULT_BRANCH`；`closeout.sh` 校验远程分支已删 |
| **Pro 上无法用规则集表达"必须关联 Issue"** | 交付与需求脱节 | 用 `policy/linked-issue` 必需检查（`closingIssuesReferences`）+ PR 模板强约束 |
| **PAT 过期导致 Projects 自动化静默失效** | 看板状态不动 | PAT 有效期纳入 `toolcheck.sh`；失败时 Action 明确报错而非静默跳过 |
| **AI Agent 以自身身份开 PR** | 审批链被绕过或缺失 | 官方规则集提供"对未归属作者的 Copilot PR 额外要求一次审批"（public preview），可选择性启用；同时要求 Agent 以**人/机器人账号身份**推送以保留可追溯作者 |
